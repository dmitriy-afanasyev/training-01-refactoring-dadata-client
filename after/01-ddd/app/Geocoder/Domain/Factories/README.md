# 🏭 Фабрики Предметной области (Domain Factories)

> Источник: Эрик Эванс, «Предметно-ориентированное проектирование», Глава 6: «Цикл существования объектов модели».

## 🎯 Назначение Фабрик в DDD

Фабрика — это механизм **инкапсуляции процесса создания**. Она освобождает клиента (Application Service, Repository) от знаний о внутренней структуре Агрегатов и Сущностей.

> 💬 **Эванс (Глава 6):**  
> _«Переложите ответственность за создание экземпляров сложных объектов и АГРЕГАТОВ на отдельный объект... ФАБРИКА инкапсулирует знания, необходимые для создания сложного объекта или АГРЕГАТА»_.

### Когда использовать Фабрику?

| ✅ Использовать Фабрику                      | ❌ Не использовать Фабрику                      |
| -------------------------------------------- | ----------------------------------------------- |
| Создание требует сборки нескольких частей    | Простой `new Entity()` без логики               |
| Нужно присвоить Tracking ID (идентичность)   | Объект-Значение (Value Object) без зависимостей |
| Требуется выбор стратегии/типа при создании  | Конструктор сам справляется с инвариантами      |
| Восстановление из хранилища (Reconstitution) | CRUD-операции без доменной логики               |

---

## 🔀 Два типа Фабрик

Эванс чётко разделяет фабрики по **цели создания**. Это не одна и та же логика.

### 1. Фабрика Создания (Creation Factory)

Создаёт **новый** объект, которого раньше не существовало.

- **Реакция на нарушение инварианта:** ❌ Выбрасывает исключение (`DomainException`). Бизнес-правило нарушено → объект не может быть создан.
- **Расположение:** Отдельный класс в `Domain/` ИЛИ фабричный метод на Корне Агрегата.
- **Пример:** `OrderFactory::createOrder()` — проверяет лимиты, генерирует номер заказа.

### 2. Фабрика Восстановления (Reconstitution Factory)

Воссоздаёт **существующий** объект из хранилища.

> ⚠️ **Важное уточнение по Эвансу:**  
> Фабрика восстановления **НЕ игнорирует** инварианты. Инварианты должны проверяться, но **реакция на их нарушение отличается**.  
> _«Фабрика, восстанавливающая объект, по-другому обрабатывает нарушение инварианта»_ (Глава 6).

- **Реакция на нарушение инварианта:** ⚡ **Не выбрасывать бизнес-исключение!** Объект уже существует в реальности. Вместо этого:
    - Логирование + создание в «повреждённом» состоянии
    - Исправление данных с фиксацией факта
    - Специальное исключение целостности данных (`DataCorruptionException`)
- **Расположение:** Отдельный класс в `Domain/`, принимающий нейтральный формат данных (array / DTO).
- **Интерфейс:** Опционален. Нужен только при наличии нескольких реализаций хранилищ с разными форматами данных.

### Сравнительная таблица

| Аспект         | 🆕 Creation Factory          | 🔄 Reconstitution Factory         |
| -------------- | ---------------------------- | --------------------------------- |
| Цель           | Новый бизнес-объект          | Гидратация из БД                  |
| Инварианты     | Строгая проверка, исключение | Проверка + альтернативная реакция |
| Присвоение ID  | Генерирует новый             | Принимает существующий            |
| Входные данные | Бизнес-параметры             | Сырые данные / DTO                |
| Зависимости    | Доменные сервисы             | Logger, возможно инфраструктура   |
| Интерфейс      | Обычно нет                   | Опционально                       |
| Клиент         | Application Service          | Repository (Infrastructure)       |

## 📍 Где размещать?

```
Domain/
├── Order/
│   ├── Entities/
│   │   └── Order.php  # reconstituteFromStorage() — статический метод
│   ├── Factories/
│   │   ├── OrderFactory.php                # 🆕 Создание нового Агрегата
│   │   └── OrderReconstitutionFactory.php  # 🔄 Восстановление из БД
│   └── Repositories/
│       └── OrderRepositoryInterface.php
```

### Правило размещения

- **Отдельная Фабрика** → когда создаётся независимый Агрегат или процесс сложен.
- **Фабричный метод на Корне Агрегата** → когда добавляется внутренняя Сущность внутрь существующего Агрегата.

> 💬 **Эванс (Глава 6):**  
> _«Если вам нужно добавить элементы внутрь уже существующего АГРЕГАТА, вы можете создать МЕТОД ФАБРИКИ на корне АГРЕГАТА... Передача контроля корню и инкапсуляция внутренней структуры — хороший компромисс»_.

---

## 🛡️ Главное правило Фабрики Восстановления

> 🚫 **НИКОГДА** не передавайте в Фабрику восстановления объекты инфраструктуры  
> (`Eloquent\Model`, `PDOStatement`, `Doctrine\Entity`).

> ✅ **ВСЕГДА** передавайте нейтральный формат: `array` или специальный DTO.

Фабрика восстановления живёт в **Доменном слое**. Зависимость от инфраструктуры разрушает границы модели.

## 🐘 Laravel-специфика

| Практика                         | Рекомендация                                        |
| -------------------------------- | --------------------------------------------------- |
| Внедрение зависимостей           | Через конструктор (Laravel Container)               |
| Генерация ID                     | Делегировать в Фабрику, а не в Сущность             |
| Eloquent Model ≠ Сущность        | Всегда использовать Фабрику восстановления как мост |
| Интерфейс Фабрики восстановления | Только при нескольких хранилищах                    |
| Тестирование                     | Можно мокать конкретный класс через Mockery         |

## ⚡ Краткое резюме

1.  **Фабрика = инкапсуляция создания.** Клиент не должен знать, как собирается объект.
2.  **Два типа — две реакции.** Создание бросает исключение. Восстановление — логирует/исправляет/помечает.
3.  **Инварианты проверяются в обоих случаях**, но обработка нарушений различается фундаментально.
4.  **Фабрика восстановления принимает array/DTO**, никогда не инфраструктурные объекты.
5.  **Размещение:** Отдельный класс для Агрегатов, фабричный метод на Корне для внутренних Сущностей.
6.  **Интерфейс для Фабрики восстановления** — опционален, не догма. Добавлять по необходимости.
7.  **Сущность предоставляет** специальный метод `reconstituteFromStorage()`, обходящий публичный конструктор.
